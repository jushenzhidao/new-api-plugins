### 上传端点调研结论：此路不通（有实证，别再试）

- 宿主文件占位符协议（docs/plugin-api/v1.md）：body 里放
  `{__fileRef:"request_file:x", encoding:"base64"|"dataUrl", mimeType?, maxBytes?}`，
  宿主在发请求前替换成编码字符串，JS 看不到字节。adaptor.go: `encodeFilePlaceholder` 只接受
  base64/dataUrl 两种 encoding → 内联后必然是 data: 或裸 base64。
- 实测用 data URL 提交 → **500 `first_frame_url[0] must use http, https, s3, or r2`**（code -32603）。
  → 上游图片地址协议白名单 = http/https/s3/r2，**data URL 不支持**；
  上游内部把插件的 `imageUrl` 叫 `first_frame_url`；**参数错误被报成 500 INTERNAL_SERVER_ERROR**（很误导）。
- 结论：宿主内联机制对该上游无效；且 buildSubmitRequest 只能发一个请求，「先上传再提交」两步做不了。
  因此本插件**不支持客户端上传文件**，只能接受可公开下载且 MIME 合规的 http(s) 外链。
- 已在插件侧按同一白名单预校验：data: / 非白名单协议 / 宿主文件占位符一律显式报错，
  避免上游回误导性 500。单测 141 项、e2e 76 项全过，同步语法扫描 clean。
- 未验证路径：官方 API（`ak_`）模式是否有独立上传端点，需 key 或官方文档。

## 把「真实端到端联调」制度化进 skill

- 起因：aivideomaker 连着两轮卡在「无真实凭据」，离线测试全绿却证明不了上游认。
- 技能新增章节「真实端到端联调（强制）」：开工即索要 Base URL + 凭据（不要收尾才要）；
  触发时机 = 新建插件 / 每个新 patch / 改动请求构建·状态映射·制品提取任一 hook；
  硬规则 = 凭据只走 `LIVE_KEY`/`LIVE_BASE` 环境变量、日志脱敏、不用 mock 顶替真实联调。
- 验证清单改两层：第 4 条标「离线层」，新增第 6 条「真实层，不可跳过」；调试决策树补
  「离线全绿但线上不可用 → 一定没做真实联调」。
- 新增通用脚手架 `assets/live-harness.mjs`（由 aivideomaker.live.mjs 泛化）：改头部三行即可用，
  支持 `--dry-run`（不联网不耗额度，只验 hook 链与拼装、凭据自动脱敏）、`--raw/--prompt/--image/
  --model/--entry/--download`。已在 aivideomaker 1.0.0 上实测 dry-run 通过。
- 实测抓到的两个真 bug（不跑就发现不了）：① 动态 import 排在凭据检查前 → 未配路径时先崩；
  ② `--image` 单张用 `inbound.image` 而插件 decoder 认 `images` 数组 → 图片静默丢失（`imageUrl: null`）。
- 用户提醒：skill 是**跨插件通用范式**，不能写成 aivideomaker 特化版。据此泛化脚手架：
  ① 制品 key 从 `listArtifacts` 推导 + 新增 `--artifact` 覆盖，删掉硬编码 `artifactKey:"video"`；
  ② render 的 artifacts map 按插件列出的 key 构造，不写死 `video`；
  ③ `--raw` 定为跨插件首选入口，`--prompt/--image` 降为多媒体类快捷方式（注明入站字段名
  可能是 prompt/text/input、image/images/image_url，不确定就用 --raw）；
  ④ SKILL 新增「通用范式，不绑定任何厂商」小节。
- 用本地 mock 上游跑通全链路时抓到第三个真 bug：aivideomaker 的 `listArtifacts` 条目
  **只有 key/type/mimeType、不带 url**，而原本要求 `item.url` 存在才认 → 制品 key 推导失败、
  回源下载静默跳过（out.mp4 根本没生成）。修法：key 只看有没有 key，url 回退到 result.url。
- 用户反馈：凭据「先要后要都行，本质是要做真实 e2e」。据此把硬约束统一收口到**收尾闸门**
  （验证清单开头的「完成的定义」）：离线层 + 真实层全过才算完成；缺真实 e2e 时回复必须分两段
  写明「已验证 / 未验证」，不许报完成。「开工就索要」降为建议（避免收尾才发现没凭据），不再强制。

## aivideomaker：用官方 OpenAPI 规范反向校验（第四轮）

- 起因：查「`ak_` 官方 API 是否有独立上传端点」时，发现站点暴露规范
  `https://aivideomaker.ai/docs/aivideo-openapi.json`（OpenAPI 3.1.0，version 1.0.15）。
- **结论：7 个端点，无任何上传端点** → 网页会话与官方 API 两种凭据形态都支持不了客户端上传，
  之前插件拒绝文件占位符的做法得到证实。
- 规范反过来印证了既有实现：提交 `POST /api/v1/generate/minimax`、查询 `GET /api/v1/tasks/{id}`、
  duration 5~20、aspectRatio 7 枚举、tier turbo/base、Error 的 `errorCode` envelope。
- 但暴露 3 个真问题，已修（1.0.0 未发布，就地改）：
  1. **官方 TaskStatus = `SUBMITTED|PROGRESS|COMPLETED|FAILED|CANCEL`**，其中 `PROGRESS`/`CANCEL`
     插件精确层没有，靠层 3 前缀兜底命中。危险在于 `CANCEL` 掉到默认 QUEUED 后上游不再变化 →
     任务永远卡轮询。已把两个值放进精确层（层 2 优先于层 3 是原则问题，不只为了覆盖）。
  2. **官方 Error schema 的 `error` 是 string**（与 `message` 并列），`failureReason` 只处理对象形态
     `.message/.msg` → 401/402 等只带 error 的错误退化成「只有码没原因」。已兼容字符串形态。
  3. **官方 Task 顶层没有 `duration`**，入参回显在 `input` 里 → `ak_` 模式完成期真实时长回填恒失败
     且静默（不报错，只是回退提交期值）。已加 `recordDuration()` 兼容两种形态，顶层优先。
- 两处**有意保留**的差异（写进 README，没让测试假装合规）：
  - `resolution`：官方枚举只有 720p/1080p，插件保留 480p（网页会话实测出片成功）。
    理由：静默夹紧到更贵的 720p 是隐性多扣费；照传让上游用明确 400 拒绝更好。
  - data URI：文档说 image 字段接受，实测被拒（且报成 500）。`ak_` 无密钥无法验证，统一按
    http/https/s3/r2 预校验。
- 新增 `.workbuddy-ai/tmp-tests/aivideomaker.openapi.mjs`：不需要凭据、不耗额度，用规范反向校验插件
  （端点命中 / 字段白名单 / 枚举类型边界 / 状态枚举遍历 / 规范形状可解析）。432 项通过，
  1 个 knownDiff（480p）显式打印。差异分两类：官方枚举更窄 → 保留宽的；文档与实测冲突 → 以实测为准但记录。
- 测试规模：合同 161 + e2e 76 + openapi 432 = **669 全绿**（合同测试从 141 涨到 161）。
- 沉淀进 skill 新章节「用官方规范反向校验（拿到 OpenAPI 时必做）」；「开始前获取事实」第 2 条
  补上「优先找机器可读规范，SPA 文档页抓取常被截断」。
- 遗留：`ak_` 官方 API 模式**始终未做真实端到端验证**（无 key），只有规范级校验。

## aivideomaker：用户填渠道 key 触发的实测诊断（第五轮）

- 用户问「渠道 key 填裸 cookie 串行不行」→ 不行，三处不对：① 格式必须是 JSON（源码第 143 行
  对非 `ak_` 非 `{` 开头直接抛错）；② 缺 `userId`（第 130 行硬性要求，否则 listModel 返回他人
  公开视频）；③ 即使前两条补上，该账号当前也提交不了。
- 帮用户从 `/api/auth.user` 取到 userId（`cmtuzdsvw...`，与上一轮成功出片的是同一账号）。
- **诊断结论（关键）：`needsCaptcha=true` 的真因是体验额度耗尽，不是凭据或 visitorId 问题。**
  三探针验证：① `listModel` HTTP 200 能列 5 个历史任务（cookie 有效）；② needsCaptcha 用全 0
  和随机 visitorId **都是 true**（排除 visitorId）；③ 真实提交返回 HTTP 200 + 空字符串，可复现。
  → **「能查到历史任务」不等于「还能出片」**，这是个很容易误判的坑：查询通、提交死。
- 站点页面文案证实：「API Key 可获 50 个体验积分」「50 积分可生成 3 个 5 秒视频并剩 5 积分」——
  用户列表里正好 3 个 succeed 任务，额度已跑完。解法是去 `/zh/app/settings/account/api-keys`
  建 `ak_` key（送积分 + 不受验证码限制 + 渠道密钥就是裸 `ak_...`，免 JSON 免 userId）。
- 规范 `securitySchemes` 确认 `apiKey` in header `name: "key"`，与插件 `apiHeaders` 一致。
- 教训：**上轮我说「/tmp 凭据已被清理」是判断错误**——`avm-live.mjs` 等文件其实还在，里面是明文
  `auth_session`。已清理全部 avm-* 凭据文件；`/tmp/avm-cdp-prof`、`/tmp/avm-real-prof`、`/tmp/avmjs`
  三个 Chrome 临时 profile 可能含登录态，已提醒用户自行处理。
- 顺带把 `avm_openapi.json` 收进 `.workbuddy-ai/tmp-tests/` 并让校验脚本默认读同目录
  （支持 `AVM_OPENAPI` 覆盖），测试不再依赖会被清理的 `/tmp`。669 项仍全绿。
